# v8-cpu-profile-decoder-mcp — Implementation Roadmap

## What We're Building

An MCP server that accepts a path to a `.cpuprofile` file (generated by Node.js, Chrome DevTools,
or `--cpu-prof` flag) and returns token-efficient bottleneck summaries instead of raw JSON.

A typical `.cpuprofile` is 5–50MB of V8 tick data. An AI agent cannot ingest this — it collapses
the context window instantly. We decode it locally and return only what matters: top functions,
hot call paths, and source-mapped TypeScript locations.

---

## V8 CPU Profile Format

Understanding the raw format is critical before building the decoder.

```json
{
  "nodes": [
    {
      "id": 1,
      "callFrame": {
        "functionName": "myFunction",
        "scriptId": "123",
        "url": "file:///app/dist/index.js",
        "lineNumber": 42,
        "columnNumber": 8
      },
      "hitCount": 17,
      "children": [2, 5]
    }
  ],
  "startTime": 1716800000000000,
  "endTime":   1716800003000000,
  "samples":    [1, 2, 1, 3, 1, 2, ...],
  "timeDeltas": [0, 100, 80, 120, ...]
}
```

Key concepts:

- **`nodes`** — call tree. Each node = one function. `children` = functions it called.
- **`hitCount`** — how many samples landed on this node (exclusive / self time).
- **`samples`** — sequence of node IDs captured at each tick interval.
- **`timeDeltas`** — microseconds between consecutive samples.
- **Exclusive time** = `hitCount * avgDelta` — time in the function body itself.
- **Inclusive time** = exclusive + sum of all children's inclusive time (recursive).
- **V8 internals to filter out**: nodes with `functionName` of `(program)`, `(garbage collector)`,
  `(idle)`, `(root)` — these are runtime overhead, not user code.

## Types (src/types.ts)

### Input: V8 format

```typescript
interface CpuProfileCallFrame {
  functionName: string;
  scriptId: string;
  url: string;
  lineNumber: number;
  columnNumber: number;
}

interface CpuProfileNode {
  id: number;
  callFrame: CpuProfileCallFrame;
  hitCount: number;
  children?: number[];
}

interface CpuProfile {
  nodes: CpuProfileNode[];
  startTime: number;
  endTime: number;
  samples: number[];
  timeDeltas: number[];
}
```

### Output: result types

```typescript
interface HotFunction {
  rank: number;
  functionName: string;
  url: string;
  lineNumber: number;
  selfTimeMs: number; // exclusive time
  totalTimeMs: number; // inclusive time
  selfPercent: number; // % of total profile duration
  totalPercent: number;
  hitCount: number;
}

interface CallTreePath {
  targetFunction: string;
  totalTimeMs: number;
  callers: Array<{
    functionName: string;
    url: string;
    lineNumber: number;
    callCount: number; // how many samples came through this path
    selfTimeMs: number;
  }>;
}

interface SourceLocation {
  originalFile: string; // TypeScript source path
  originalLine: number;
  originalColumn: number;
  originalFunction: string;
}

interface SourceCorrelationResult {
  resolved: Array<{
    rank: number;
    generatedUrl: string;
    generatedLine: number;
    source: SourceLocation | null;
    selfTimeMs: number;
    selfPercent: number;
  }>;
  sourcemapErrors: string[];
}
```

## Core Algorithm (src/decoder.ts)

### Step 1: Parse + build node map

```
parse JSON from file path
→ build Map<id, node> for O(1) lookup
→ calculate avgDelta = sum(timeDeltas) / timeDeltas.length
→ totalDurationMs = (endTime - startTime) / 1000
```

### Step 2: Compute exclusive time per node

```
for each node:
  selfTimeMs = node.hitCount * avgDelta / 1000
```

### Step 3: Compute inclusive time (recursive DFS)

```
function inclusiveTime(nodeId):
  node = nodeMap[nodeId]
  total = node.selfTimeMs
  for child in node.children:
    total += inclusiveTime(child)
  return total
```

Cache results to avoid recomputation on shared subtrees.

### Step 4: Filter + rank

```
filter out: functionName in ['(program)', '(garbage collector)', '(idle)', '(root)']
filter out: url is empty or starts with 'node:' (Node internals)
sort by selfTimeMs descending
return top N (default: 10)
```

### Step 5: Find callers for analyze_call_tree_path

The profile tree is top-down (parent → children). To find callers of a function:

```
build reverse map: childId → parentId[]  (during initial parse)
for target function name:
  find all nodes matching that name
  for each: walk up the reverse map to collect caller chain
  aggregate by call count from samples array
```

### Step 6: Source map resolution (src/sourcemap.ts)

```
for each hot function url (e.g. file:///app/dist/index.js:42:8):
  1. strip file:// prefix → absolute path
  2. look for <path>.map file alongside it
  3. if found: use source-map library to resolve original position
  4. return original .ts file + line + function name
  5. if not found: return null (graceful degradation)
```

Source map resolution is best-effort — if no `.map` file exists, we still return the compiled JS
location. The tool remains useful without TypeScript source maps.

## Tools (src/index.ts)

### `extract_hottest_functions`

Input:

```typescript
{
  profile_path: string         // absolute path to .cpuprofile file
  top_n?: number               // default 10, max 50
  min_self_percent?: number    // filter out noise (default 0.5%)
  include_node_internals?: boolean  // default false
}
```

Output: `HotFunction[]` ranked by selfTimeMs.

---

### `analyze_call_tree_path`

Input:

```typescript
{
  profile_path: string
  function_name: string        // exact or partial match
  top_callers?: number         // how many callers to return (default 5)
}
```

Output: `CallTreePath` — who calls the target and how often.

---

### `correlate_source_code`

Input:

```typescript
{
  profile_path: string
  top_n?: number               // default 10 hottest functions to resolve
  sourcemap_dir?: string       // override dir to look for .map files
}
```

Output: `SourceCorrelationResult` — hottest functions mapped to original TypeScript.

---

## Error Handling

- File not found → clear error message with path
- Invalid JSON → parse error with hint (not a .cpuprofile?)
- Empty profile / zero samples → return empty result with warning
- Source map missing → include in `sourcemapErrors`, still return JS location
- Function name not found in `analyze_call_tree_path` → return closest matches

## Open Questions (decide before coding)

1. **Input: file path vs raw JSON string?**
   → File path. The whole point is decoding large files the agent can't read directly.

2. **Function name matching in `analyze_call_tree_path`: exact or partial?**
   → Partial (includes). Agent might not know the exact internal name.

3. **What to do with anonymous functions `(anonymous)`?**
   → Include them, but label with url+line so they're still identifiable.

4. **Max file size guard?**
   → Warn if > 100MB, still process (just takes longer).
